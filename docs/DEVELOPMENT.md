## Conventions

- **Each experiment directory is self-contained**: its own `code/`, `eda/`, `data/` and its own
  `system_prompts_builder.py` + `questionnaires.py`, whose versions deliberately differ across
  experiments (never share a root-level module). In Exp3 both helpers live once at `code/` root and
  the EDA package imports the same files.
- **Dependencies:** `requirements.txt` is generated by [gen_requirements.py](../gen_requirements.py),
  a curated list of direct imports pinned to the installed versions; regenerate it after upgrading
  a package.

## API keys

The patient simulator and the oracle call the OpenAI API; the therapist base model is pulled from
Hugging Face. For training, keys are resolved at runtime — **Colab `userdata` secrets → environment
variables → local key files** — by `init_openai_client` / `authenticate` in
[Exp3_PTO_GRPO/code/_shared/runtime.py](../Exp3_PTO_GRPO/code/_shared/runtime.py). The held-out judge
(scoring only) reads `ANTHROPIC_API_KEY` or `anthropic_key.txt` at the experiment root
([scoring/judge.py](../Exp3_PTO_GRPO/eda/eda_analysis/scoring/judge.py)).

| Secret | Colab | Local |
|---|---|---|
| OpenAI | `userdata["OPENAI_API_KEY"]` → env → file | env (`OPENAI_API_KEY`) → file |
| HF token | `userdata["huggingface"]` → env → file | env (`HF_TOKEN`/`HUGGINGFACE_TOKEN`) → file |
| W&B | `userdata["wandb"]` | env `WANDB_API_KEY` |

Locally, put `openai_key.txt` and `HF_key.txt` (and `anthropic_key.txt` for the held-out judge) in
`Exp3_PTO_GRPO/`; all three are git-ignored, never commit them. **The first two are required even
when the keys are set as environment variables**, because they double as the marker of the
experiment root: the EDA and the trainers walk up from the working directory to the folder that
holds both. Without them `import eda_analysis` raises, and the trainers fall back to the working
directory as the root (so their outputs land in the wrong place). The **HF token is needed locally
too** — Llama-3.2-1B is gated. On Colab all secrets come from **Colab Secrets**, never the `.txt`
files.

## Data & large artifacts (not in git)

This repository tracks **code, notebooks, docs and the rendered analysis tables/figures** only.
Excluded by [.gitignore](../.gitignore) because they are large and/or regenerable:

| Path | What it is | How it comes back |
|---|---|---|
| `**/data/` | Generated conversations, preference trees, adapters, oracle + held-out-judge scores (multiple GB) | Regenerated by running the pipelines |
| `.venv/` | Python virtual environment | `pip install -r requirements.txt` |
| `**/.emb_cache/`, `**/emb_cache_words/` | Sentence-embedding caches | Recomputed by the notebooks that use them |
| `**/eda/.eda_cache/` | Exp3 EDA parquet cache (content-keyed) | Rebuilt on the next EDA run; `eda_analysis.reset_cache()` to clear |
| `HF_key.txt`, `openai_key.txt`, `anthropic_key.txt` | API credentials (the first two also mark the experiment root) | Provide your own (above) |

How it is regenerated:

- **Exp3 self-loop.** `GRPO_Exp3` and `PTO_Exp3` regenerate their training data every iteration from
  the current policy (the policy simulates 96 conversations → per-turn prompts or preference
  branches → update). Those conversations double as the evaluation set of that policy, so trained
  iterations need no separate generate-eval step.
- **No cross-experiment data.** Exp3 regenerates everything it needs; it shares no data with Exp2.
- **Evaluation.** `Exp3_PTO_GRPO/eda/notebooks/scoring/Run_Eval.ipynb` scores conversations into the
  score lake, `Exp3_PTO_GRPO/data/eval_scores/judge=<tag>/rep=<r>/`.

⚠ **The score lake is the only copy of the oracle and judge scores, which cost real API money to
produce, and re-scoring it is not affordable** (spend and the cost constraint:
[STATUS.md](../STATUS.md)). That is why it sits on a Google Drive symlink rather than local-only,
and why `data/eval_scores/_parquet/` matters: it folds the lake into a few dozen parquet files
(one per judge × replicate × metric) that are cheap to copy elsewhere.

⚠ **The `README.md` files inside the run directories are auto-generated model cards** — PEFT/TRL
writes one beside every saved adapter (`data/{grpo,pto}_Exp3/runs/**/iteration_*/adapter/README.md`,
`.../training/README.md`, `.../training/checkpoint-*/README.md`). Do not delete them or treat them as
project docs.

To share raw datasets or trained adapters, host them externally (Hugging Face Hub, Zenodo, Google
Drive) rather than committing them.

## Sync: Colab ↔ local

Training runs on Colab and writes into mounted Drive; the EDA runs locally and reads the same bytes.
No rclone is involved.

**Results pull — Google Drive Desktop.** `data/eval_scores`, `data/grpo_Exp3` and `data/pto_Exp3`
are **directory symlinks** into `G:\My Drive\Thesis_PTO_GRPO\Exp3_PTO_GRPO\data\<name>`. Colab
writes to mounted Drive → Drive Desktop (in **streaming** mode, low disk) surfaces it locally → the
files appear inside the repo, and the EDA reads through the link unchanged (every read goes via
`WORKSPACE_ROOT/data/...`). The EDA only opens `conversations/` and the score lake, so streaming
downloads just those; the big artifacts (`runs/`, adapters, `*.safetensors`) are never read locally
and also live on the HF Hub and W&B.

Re-create the links with Windows **Developer Mode** on, using `mklink` — **not** PowerShell
`New-Item -ItemType SymbolicLink`, which under WinPS 5.1 ignores Developer Mode and still demands
admin:

```powershell
$D = "G:\My Drive\Thesis_PTO_GRPO\Exp3_PTO_GRPO\data"
$R = "C:\Users\baruc\Desktop\Projects\Thesis_PTO_GRPO\Exp3_PTO_GRPO\data"
cmd /c "mklink /D ""$R\eval_scores"" ""$D\eval_scores"""
cmd /c "mklink /D ""$R\grpo_Exp3""   ""$D\grpo_Exp3"""
cmd /c "mklink /D ""$R\pto_Exp3""    ""$D\pto_Exp3"""
```

To undo, delete the **link** (`Remove-Item "$R\grpo_Exp3"`) — the Drive data is untouched.

**Code push (local → Drive, `code/` only) is manual and additive.** The whole `code/` tree lives at
`G:\My Drive\Thesis_PTO_GRPO\Exp3_PTO_GRPO\code\` — all Colab needs; open a
`train_*_Iterative.ipynb` from there. Do **not** push `data/` (the symlink targets already live in
Drive) or `eda/` (local-only). After editing code locally, **drag the `code` folder** onto the
Drive `Exp3_PTO_GRPO\` parent — a merge that adds and overwrites but **never deletes**. Let Drive
Desktop finish syncing (tray ✓) before running the Colab cell.

⚠ **Never run `robocopy /MIR`, or any other delete-extras mirror, without Lior's explicit
go-ahead.** An exact mirror is the only thing that also removes files renamed or deleted locally,
which is why it is destructive on the destination:

```powershell
# DESTRUCTIVE on the destination. Requires explicit go-ahead.
robocopy "C:\Users\baruc\Desktop\Projects\Thesis_PTO_GRPO\Exp3_PTO_GRPO\code" `
         "G:\My Drive\Thesis_PTO_GRPO\Exp3_PTO_GRPO\code" /MIR /XD __pycache__
```

`rclone sync A B` has the same asymmetry (it deletes extras in B) — use `copy` for additive and
`check` for a dry-run diff.

## EDA in one paragraph

`Exp3_PTO_GRPO/eda/eda_analysis/` is the analysis package; one notebook per results family
(`eda/notebooks/{arms,lookahead,method,compute,measurement}/<sub>.ipynb`; the notebook path is its
results family). Each notebook's cell 1 is
`eda_analysis.EdaConfig(family="<top>/<sub>", judge=os.environ.get("EDA_JUDGE", ""))` →
`notebook_setup(cfg)`; figures save as PNG and tables as Markdown + Excel (+ JSON ledgers) into
`eda/results/<top>/<sub>/{figures,tables}/[<judge>/]`. Regenerate everything with
`python tools/render_results.py` from `Exp3_PTO_GRPO/eda/` (`--top lookahead`,
`--family arms/outcomes --judge <tag>` for one unit), then run `python -m eda_analysis._selfcheck`.
Full guide: [Exp3_PTO_GRPO/eda/README.md](../Exp3_PTO_GRPO/eda/README.md).

## Hardware

Developed on Windows with an RTX 5070 Ti (12 GB VRAM), CUDA 12.8, torch 2.11.0+cu128. Training runs
on Colab A100s; evaluation and the EDA run locally. On the local card an over-budget VRAM request
reboots the machine rather than raising an out-of-memory error — see
[CLAUDE.md § Exp3 · Gotchas](../CLAUDE.md#exp3--gotchas) before raising a generation batch size.
